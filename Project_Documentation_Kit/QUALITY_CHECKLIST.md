# Documentation Quality Checklist

## Scope and evidence

- [ ] Problem, users, outcomes, phase boundaries and exclusions are explicit.
- [ ] Confirmed decisions have a basis; proposals and assumptions are labeled.
- [ ] Questions have IDs, impacts, owners and affected scope; blockers are visible.
- [ ] Future features are separated from current requirements.
- [ ] Important research/feasibility claims have sources and dates or recorded gaps.
- [ ] No reference-product features, branding, estimates or stack were inherited as facts.

## Specification depth

- [ ] Every in-scope requirement has acceptance and planned verification.
- [ ] All relevant roles, screens/interfaces, operations and entities are covered.
- [ ] Flows include failure, denial, repetition/concurrency and recovery where applicable.
- [ ] Contracts agree on types, names, units, ownership, statuses and errors.
- [ ] Access matrix matches interface, API and data enforcement.
- [ ] Design covers states, accessibility and supported platforms.
- [ ] Data lifecycle, specialist modules, integrations, deployment and recovery are addressed.
- [ ] N/A sections explain why, without inventing features to fill them.
- [ ] Roadmap has dependencies, observable outcomes and exit criteria.

## Consistency and usability

- [ ] Internal links resolve and document paths match the index.
- [ ] IDs are stable and references resolve; traceability gaps are explained.
- [ ] Terminology, metadata, phase scope and version/status are consistent.
- [ ] No authoring placeholders remain except explicit TBD/question records.
- [ ] Complete, Accepted, Implemented and Passed labels have appropriate evidence.
- [ ] Proposed commands are labeled; no secrets or private sample data appear.
- [ ] Seven project entry files summarize and link without conflicting copies.
- [ ] Existing docs and both reusable kits are preserved.

## Delivery

- [ ] BUILD_READINESS.md identifies the scope ready to implement and exact blockers.
- [ ] MEMORY.md identifies the first ready task and unrun checks.
- [ ] Output location, coverage, open decisions and next action are reported.
- [ ] Documentation review is clearly separate from executing application tests.
